# Roadmap

This roadmap shows the order the project plans to build in. It is a direction, not a set of dates, and it changes as contributors join and priorities shift. Open an issue to propose a change.

The phases follow the six layers in [`docs/01-architecture.md`](docs/01-architecture.md), built from the foundation up so each phase produces something usable on its own.

> **Implementation review (2026-06-06).** Phases 0–4 were audited against the committed code, tests, and control data. Ground truth: `go test ./...`, `go vet`, and `gofmt -l` are all clean, the build is stdlib-only (no external dependencies), and `fabric validate`/`assess` pass on the shipped controls. The net-new engine (controls, five evidence producers, ledger, registry, eval gate) is fully implemented and test-covered. Two claims were corrected as overstated: the Sigstore admit path is **not** exercised in CI, and the SBOM/SLSA reference pipeline is **not started**. The Phase 1 kind-cluster admission proof, previously flagged as not reproducible, has since been closed: a committed e2e harness (`test/e2e/admission.sh`) now reproduces the deny/admit/PolicyReport proof and runs as a kind-based CI job. Each phase below carries a dated review note.

## Phase 4: AI agent governance (in progress)

- Agent and prompt/tool registry as versioned artifacts. **Done:** the `internal/registry` package models agents, prompts, and tools as versioned artifacts, and `fabric registry validate` checks versioning, agent ownership, reference resolution, and duplicate ids. A starter registry lives under `registry/`.
- Gateway policy and interaction tracing. **Done:** `fabric trace` is a fourth evidence producer that judges each gateway interaction against the registry's qualified surface (an undeclared prompt or tool, or an unregistered agent, is off-policy) and keys records to `eu-ai-act-12-record-keeping`, feeding the same ledger. The inline runtime gateway is now built too: `internal/gateway.Decide` is the pure admission decision and `fabric gateway` serves it over HTTP, admitting (200) or blocking (403) each interaction at request time and logging it in the shape `fabric trace` consumes. `evidence.FromAgentTraces` delegates to the same `Decide`, so the inline block and the after-the-fact trace are one definition of "qualified". Only the `ListenAndServe` shell sits outside the test-first core; the decision and log shape are unit-covered.
- Evaluation gates before promotion. **Done:** the `internal/eval` package models the promotion gate as authoritative policy (required suites and a failure budget), and `fabric eval-gate` is a fifth evidence producer that records whether a version was cleared to ship, keyed to `eu-ai-act-15-accuracy-robustness`.

**Review (2026-06-06): the implemented (data-and-logic) scope is done and accurate.** Verified: `internal/registry` + `fabric registry validate`, `internal/eval` + `fabric eval-gate`, and the `fabric trace` producer are all implemented and test-covered; the new `eu-ai-act` catalog controls validate and assess satisfied; a starter registry ships under `registry/`. Minor hardening option: the Phase 4 CLI commands are covered by `go test` but, unlike the Phase 1 commands, are not invoked as dedicated CI steps.

**Update (2026-06-07): the inline runtime gateway is now built.** The previously open item — a gateway that enforces policy at request time rather than evaluating its interaction log after the fact — is implemented test-first: `internal/gateway.Decide` is the pure admission decision (table-tested) and `gateway.Server` is an HTTP handler (httptest-covered: 200 admit / 403 block, plus the interaction-log line it writes). `fabric gateway` wires them behind a thin `ListenAndServe` shell, which is the only part not under unit test. The decision is shared with `evidence.FromAgentTraces` through `Decide`, so inline enforcement and post-hoc evidence cannot disagree about what is qualified, and the gateway's JSON-lines log is consumed directly by `fabric trace`. The gateway also screens request **content**: `gateway.Guardrail` (a compiled set of named regexp rules, `--guardrail <policy-file>`) blocks input matching a sensitive-data or prohibited-content pattern after the registry check passes, and the log records the verdict but never the raw input. What remains for a production deployment (and is out of scope for the test-first engine here) is the rest of the gateway surface the layer doc describes — model/tool allow-listing of live LLM/MCP traffic, **output** (not just input) screening, rate and cost limits — and OpenTelemetry-native trace ingestion.

**Update (2026-06-07): the gateway is now proven end-to-end, and a content-block fidelity gap was closed.** A committed harness, [`test/e2e/gateway.sh`](test/e2e/gateway.sh) (wired into CI as the `gateway-e2e` job), runs the real `fabric gateway` HTTP server and asserts the live behaviour the unit tests cannot reach through `ListenAndServe`: a qualified interaction is admitted (200), an unregistered agent is blocked (403), and a registered agent whose input carries a sensitive-data pattern is blocked (403) with the raw input never written to the log — then the gateway's own log is fed through `fabric trace` and the ledger chain verifies. Proving this end-to-end surfaced a real fidelity gap: `evidence.FromAgentTraces` re-derived each verdict from the registry alone, so a request the gateway blocked on **content** (registration was fine, the guardrail fired) rolled up as *satisfied* — guardrail enforcement was invisible in the audit trail. Fixed test-first: the trace producer now honors a logged `allowed:false` (the gateway's recorded verdict) as not-satisfied, while a trace with no recorded verdict (an OTel envelope) is still judged by `gateway.Decide`. The e2e now asserts the guardrail-blocked interaction is not-satisfied, end-to-end through the real binary.

**Update (2026-06-07): model allow-list and output screening now ship.** Two more strands of the layer doc's gateway are built test-first. (1) *Model allow-list:* `gateway.Decide` now screens the model a request declares (`Request.Model`) against the agent's qualified `registry.Agent.Model` and blocks an off-list model — non-strict by design (it fires only when the request declares a model and the agent pins one), so the post-hoc trace-evidence path, which re-derives the same decision without a model, is unaffected. (2) *Output screening:* the gateway now screens generated **output**, not just input — `POST /output` runs an `OutputRequest` through the same compiled guardrail (200 pass / 403 block) and logs the verdict (a `phase:"output"` entry) without ever writing the raw output. Both are unit-covered, and the `gateway.sh` e2e is extended to assert the model-mismatch block and the output-screening block over the real binary. What remains for a production deployment (still out of scope for the test-first engine here): enforcing the allow-list and guardrails on *live* LLM/MCP traffic by proxying the model and tool calls rather than screening what each request declares, rate and cost limits.

**Update (2026-06-07): OpenTelemetry OTLP/JSON trace ingestion now ships.** `fabric trace` (`evidence.FromAgentTraces`) now also consumes the OTLP/JSON trace export (`{"resourceSpans":[…]}`) directly, alongside the `{"traces":[...]}` envelope and the gateway's JSON-lines log. Each span is flattened into one interaction — its attributes (`id`, `agent`, `prompt`, `tools`, and the gateway's recorded `allowed` verdict) mirror the JSON-lines field names, the span id is the interaction id when no `id` attribute is set, and `startTimeUnixNano` is the observed time — so a standard OpenTelemetry trace pipeline feeds the evidence ledger with no reshaping step. Implemented test-first in `internal/evidence`. This closes the docs/05 claim that every agent action is traced with OpenTelemetry; what is still genuinely open for Phase 4 is only the live-traffic proxy (today the gateway screens what each request declares) and rate/cost limits.

**Update (2026-06-07): rate and cost limits now ship.** The gateway gains a per-agent fixed-window budget as the third admission gate after the registry decision and the content guardrail. `gateway.Limiter` (`internal/gateway/limit.go`, built test-first) charges each interaction that clears the first two gates against the agent's `Limits{max-requests, max-cost, window}`: a registered agent running a declared prompt with clean input is blocked once it exhausts its request count or caller-asserted cost in the current window, which bounds runaway volume and spend from a non-deterministic agent. A blocked request consumes no budget, a zero on either axis is unlimited on that axis, a zero window is a lifetime budget, and an unconfigured agent or nil limiter enforces nothing. `Request.Cost` carries the asserted per-interaction cost, and `fabric gateway --limits <limits-file>` loads a JSON map of agent to budget with human-readable window durations ("1h", "30m"), validated before the listener binds. Unit- and CLI-covered. With this, the only Phase 4 strand still open is the **live-traffic proxy** — enforcing the registry surface, guardrails, and budgets on actual LLM/MCP calls by proxying them, rather than on what each request declares to the gateway.

**Update (2026-06-07): the live-traffic proxy now ships.** `gateway.Proxy` (`internal/gateway/proxy.go`, built test-first) is a reverse proxy in front of an upstream LLM/MCP endpoint that applies the same three gates — registry decision, content guardrail, rate/cost limit — to the agent's *real* request on the wire rather than to a request declared to the gateway. `RequestFromHTTP` recovers the gateway `Request` from the live call (agent and prompt from `X-Fabric-Agent`/`X-Fabric-Prompt` headers, model and tool names from the JSON body across both the OpenAI and Anthropic tool shapes, message text as the screened input) and leaves the body readable so the original payload forwards unchanged; an admitted request is forwarded via `httputil.ReverseProxy` and a blocked one gets 403 **without ever reaching the upstream**. `fabric gateway-proxy <registry-dir> --upstream <url>` runs it, sharing the gateway's `--log`/`--guardrail`/`--limits` wiring. The whole thing is unit-covered against a fake upstream (the extraction, the gates, and the forward/block decision); only `ListenAndServe` is the network shell. This closes the last open Phase 4 strand the layer doc describes — the gateway now enforces on live traffic, not just on what a caller declares. The request-side surface — identity, model/tool allow-list, content guardrail, and rate/cost budgets — is enforced on the wire.

**Update (2026-06-07): the proxy now screens the upstream response too.** When a guardrail is configured, `gateway.Proxy` screens the upstream's *response* body before it reaches the agent (the same guardrail applied on the way back via `httputil.ReverseProxy`'s `ModifyResponse`): a secret or prohibited content the model returns is blocked (403, the body never forwarded) and logged as a `phase:"output"` interaction without leaking it, while a clean response passes through unchanged and an unguarded proxy streams responses untouched. Built test-first against a fake upstream. With this the proxy enforces content policy on both sides of a live interaction. Phase 4's data-and-logic scope is now complete; the one honest residual is that the response screen buffers the body, so incremental screening of *streamed* (SSE) responses — and a reference deployment — are operational hardening rather than new control logic.

**Update (2026-06-07): streamed-response screening now ships, and both proxy proofs are end-to-end.** Two items from the note above are closed. (1) *Incremental SSE screening:* `gateway.Proxy` now screens a *streamed* (Server-Sent Events) upstream response event by event instead of buffering the whole body — a `screeningReader` splits the stream on event boundaries, releases each event to the agent only once it passes the guardrail, and cuts the stream at the first event a rule catches (the dirty event and everything after withheld, the verdict logged once). Because the upstream's 200 is already on the wire when streaming begins, a mid-stream block truncates the response before the offending event rather than answering 403, and the secret still never reaches the agent; a clean stream forwards unchanged and is logged allowed at EOF, while a non-streamed response keeps the buffer-and-replace 403 path. Built test-first against a flushing SSE upstream. (2) *Live proxy e2e:* [`test/e2e/gateway-proxy.sh`](test/e2e/gateway-proxy.sh) (CI job `gateway-proxy-e2e`) runs the real `fabric gateway-proxy` in front of a stdlib-only fake upstream and asserts forward/registration-block/guardrail-block/model-block plus the response-side secret block over live HTTP, then feeds the proxy's own log through `fabric trace` into a ledger (3 satisfied, 4 not-satisfied) and verifies the chain — exercising the `ListenAndServe` shell and the real reverse-proxy forwarding the unit tests cannot. With both buffered and streamed response content enforced on the wire and proven end-to-end, the only remaining Phase 4 item is operational: a reference deployment.

## Phase 5: Cross-sector profiles (done)

**Update (2026-06-07): the crosswalk engine and worked DORA and NIS2 crosswalks are in.** `internal/crosswalk` and `fabric crosswalk <crosswalk-file> <source-ledger>` reuse the existing engine and evidence base: a crosswalk maps a target-sector citation onto the controls the Fabric already enforces, and `crosswalk.Apply` rolls a source ledger's evidence up under those citations — a citation is satisfied only when every anchor control behind it is currently satisfied (posture's latest-observation rule, reused so the crosswalk cannot disagree with posture). A DORA catalog/crosswalk (`controls/catalogs/dora.json`, `controls/crosswalks/dora.json`) and a NIS2 catalog/crosswalk (`controls/catalogs/nis2.json`, `controls/crosswalks/nis2.json`) each answer four citations from the existing Part 11, Annex 11, and supply-chain controls, proven end to end against a real ledger — two sectors on the same engine. Crosswalks are now first-class control-tree artifacts: `loader.Load` reads `<root>/crosswalks/*.json` and `fabric validate` checks each crosswalk's referential integrity (every anchor and target resolves to a real control, no duplicate or empty mappings), so a typo'd anchor is caught at validate time rather than silently making a citation un-satisfiable. An ISO/IEC 42001 catalog/crosswalk (`controls/catalogs/iso-42001.json`, `controls/crosswalks/iso-42001.json`) extends crosswalking to the agent layer: its verification/validation and event-logging controls are answered by the EU AI Act eval-gate and record-keeping controls the Phase 4 agent governance already evidences. With DORA, NIS2, and ISO 42001 all crosswalked from existing GxP and agent-layer controls — and crosswalks validated like every other artifact — the Phase 5 scope is met; further sector profiles are additive data on the same engine.
