# Changelog

All notable changes to this project are recorded here. The format follows Keep a Changelog. The project moves to semantic versioning once it publishes releases.

## [Unreleased]

### Added

- Reference architecture and layer documentation (`docs/00` through `docs/10`).
- Architecture decision records 0001 through 0007, covering OSCAL, Kyverno, Sigstore, the open-core model, GitOps change control, Open Cluster Management, and the AI/MCP gateway.
- Reference architecture diagram (`reference/architecture.drawio`).
- Open-core project setup: license, notice, governance, contribution guide, code of conduct, security policy, roadmap, maintainers, and GitHub issue and pull-request templates.
- OSCAL controls layer: catalogs (Annex 11, 21 CFR Part 11), the pharma MES baseline profile, and component definitions expressed in the OSCAL rule_set convention so the data is Compliance-to-Policy compatible.
- `fabric` CLI (`cmd/fabric`) with `validate`, `report`, `assess`, `policies`, and `generate` commands; standard-library-only Go, developed test-first.
- Kyverno policy library under `policies/kyverno/` with `fabric.control-id` traceability, verified by the `policies` command and in CI.
- Native policy composer (`internal/generate`, `fabric generate`) as an interim stand-in for Compliance-to-Policy: it composes the deployable policy set for the selected controls. It is intentionally swappable for C2P and does not author policy.
- Sigstore keyless image-signature verification at admission (`policies/kyverno/verify-image-signatures.yaml`) mapped to the new `cfr-part-11-10a-system-validation` control. The deny path (unsigned image rejected) is proven on a kind cluster; the signed-image admit path is exercised in CI, which holds the signing identity.
- Change-control evidence extractor (`internal/evidence`) and `fabric evidence` command: derives an attributable, time-stamped change-control record (author, approvers, merge timestamp, merge commit) from `gh pr view --json` output, and flags records that are not valid authorized changes per Annex 11 / Part 11. Exits non-zero on findings so it can gate CI.
- The `annex11-10-change-control` control and a non-Kyverno `gitops` component that maps it to a `gitops-pr-evidence` check, selected in the pharma MES baseline. Coverage and assessment count it satisfied, while the Kyverno-only `policies` and `generate` commands ignore it.
- `fabric evidence <pr-json-file> <control-id>` emits a machine-readable evidence-ledger record keyed to the control (the `docs/07` data model), with the change record embedded as raw evidence; it exits non-zero when the change is not a valid authorization.
- Append-only, tamper-evident evidence ledger (`internal/ledger`): records are chained by a SHA-256 hash over the previous hash and the record, persisted as JSON Lines, so any later mutation, deletion, or reordering breaks the chain and is detectable.
- `fabric evidence ... --ledger <path>` appends the evidence record to a ledger (a flagged change is recorded too; the exit code still reflects findings), and `fabric ledger verify <path>` walks the chain and exits non-zero if it has been tampered with.
- `fabric ledger assess <path>` normalizes the ledger's evidence records into an OSCAL assessment-results document (one finding per record, control-id and status carried through) — the same model `fabric assess` emits — and exits non-zero when any finding is not-satisfied, so CI can gate on observed evidence.
- Control-posture rollup (`internal/posture`) and `fabric ledger posture <path>`: for each control, the latest observed result (latest record wins), how many times it has been observed, and how many of those were lapses. This is the day-to-day posture view for platform and quality teams, distinct from the design-time coverage `fabric report` shows; it exits non-zero when any control currently has an open gap.
- A second evidence producer: `fabric policy-report <report-json-file> <policies-dir>` turns a Kyverno PolicyReport (`kubectl get policyreport -o json`) into evidence records keyed to the controls the reported policies enforce. The policy-to-control mapping is read from the policy library's `fabric.control-id` annotations (`policies.ControlsByPolicy`); a pass is satisfied, fail/error/warn are not-satisfied, and skip produces no evidence. Records feed the same ledger, `--ledger <path>` to append. This makes the ledger and posture view multi-source rather than change-control only.
- A third evidence producer: `fabric drift <argo-apps-json-file> <control-id>` turns Argo CD application sync status (`kubectl get applications -o json`) into drift evidence keyed to a control. A Synced application means the running state still matches the validated state held in Git (satisfied); OutOfSync is drift away from the qualified state (not-satisfied). Records feed the same ledger.
- The `annex11-11-periodic-evaluation` control (EU GMP Annex 11 - confirm the system remains in a valid state), implemented by the `gitops` component's new `gitops-drift-evidence` check and selected in the pharma MES baseline, so coverage, assessment, and posture recognize drift detection as enforcement behind a control.
- Phase 4 agent governance: the `internal/registry` package models AI agents, prompts, and tools as versioned artifacts (`<root>/agents`, `prompts`, `tools` JSON trees, mirroring the OSCAL controls layout), and `fabric registry validate <registry-dir>` checks the registry for internal consistency — every artifact is versioned, every agent has an owner, every prompt and tool reference resolves, and no id is duplicated. A starter registry ships under `registry/`.
- A fourth evidence producer: `fabric trace <traces-json-file> <registry-dir> <control-id>` turns a gateway interaction log into agent-governance evidence, judging each interaction against the registry's qualified surface. An interaction is satisfied only when the agent is registered and used its declared prompt and tools; an unregistered agent or any undeclared prompt or tool is off-policy (not-satisfied). Records feed the same ledger, `--ledger <path>` to append, so agent behavior rolls up through `fabric ledger assess` and `fabric ledger posture` like every other source. This ties the registry to runtime: the registry is the qualified surface, the trace is what actually happened.
- The `eu-ai-act-12-record-keeping` control (EU AI Act Article 12 - automatic record-keeping over the system's lifetime) in a new `eu-ai-act` catalog, implemented by a non-Kyverno `agent-gateway` component's `agent-interaction-tracing` check and selected in the pharma MES baseline, so coverage, assessment, and posture recognize agent interaction tracing as enforcement behind a control.
- Agent evaluation gates: the `internal/eval` package models the promotion gate as authoritative policy (which evaluation suites must have been run, and how many failing cases are tolerated), kept separate from the run it judges so a run cannot grade itself. `Gate.Evaluate` blocks a version that left a required suite untested or exceeded its failure budget.
- A fifth evidence producer: `fabric eval-gate <eval-run-file> <gate-file> <control-id>` runs an agent version's evaluation results through the gate and records the verdict — satisfied when the version would promote, not-satisfied when the gate blocks it. Records feed the same ledger, `--ledger <path>` to append, so promotion decisions roll up through `fabric ledger assess` and `fabric ledger posture`.
- The `eu-ai-act-15-accuracy-robustness` control (EU AI Act Article 15 - accuracy, robustness, and cybersecurity) in the `eu-ai-act` catalog, implemented by a non-Kyverno `eval-gate` component's `agent-eval-gate` check and selected in the pharma MES baseline, so coverage, assessment, and posture recognize pre-promotion evaluation gating as enforcement behind a control.

- A sixth evidence producer: `fabric provenance <provenance-json-file> <expected-builder-id> <control-id>` turns a SLSA build-provenance attestation (an in-toto v1 statement, the decoded payload from `cosign verify-attestation --type slsaprovenance --output json`) into evidence records, one per attested artifact. A record is satisfied only when the statement is a SLSA provenance attestation built by the expected trusted builder, so an artifact built outside the trusted pipeline is detectable; records feed the same ledger, `--ledger <path>` to append.
- The `cfr-part-11-10a-system-validation` control is now additionally implemented by a non-Kyverno `supply-chain` component's `provenance-attestation` check, so build-provenance attestation is recognised as enforcement behind the control alongside the Kyverno `verify-image-signatures` admission check.
- A seventh evidence producer: `fabric sbom <sbom-json-file> <policy-file> <control-id>` turns a CycloneDX SBOM (as `syft -o cyclonedx-json` emits) into evidence keyed to a control, judging the image's component inventory against a banned-components policy. It is the content counterpart to `fabric provenance`: provenance attests how the image was built, the SBOM attests what is inside it. An empty inventory is not-satisfied (no evidence of contents); otherwise each banned component present (by exact name and version, or by name at any version) yields a not-satisfied record naming it, and a clean non-empty inventory yields one satisfied record for the image. Records feed the same ledger, `--ledger <path>` to append.
- The `cfr-part-11-10a-system-validation` control gains a second `sbom-content` rule on the `supply-chain` component (`sbom-inventory` check), so SBOM-content screening is recognised as enforcement behind the control alongside build-provenance attestation and the Kyverno signature check.
- Reproducible Phase 1 admission e2e harness (`test/e2e/admission.sh`), wired into CI as a kind-based job: it stands up a kind cluster, installs Kyverno, applies the Phase 1 policy library (the image-signature policy excepted — Phase 2), and asserts all three enforcement behaviours — a non-compliant Pod is denied at admission, a compliant Pod is admitted, and Kyverno's background scan produces a PolicyReport that `fabric policy-report` turns into satisfied evidence the ledger accepts and verifies. This closes the previously non-reproducible "proven on a kind cluster" claim.
- Reproducible Phase 2 supply-chain e2e harness (`test/e2e/supply-chain.sh`): a locally runnable, key-based proof of the whole trusted-delivery chain. It generates a cosign key pair, builds and pushes a signed and an unsigned image to ttl.sh (an ephemeral OCI registry), generates an SBOM with syft, attaches the SBOM and a SLSA provenance attestation and signs the image with cosign, then on a live kind cluster running Kyverno asserts that the unsigned image is denied at admission and the signed image is admitted, and finally turns the verified provenance attestation into satisfied control evidence (`cosign verify-attestation` → `fabric provenance`) that the ledger accepts and `fabric ledger posture` reports clean. cosign is pinned to v2 because cosign v3 defaults to the new Sigstore bundle signature format that the cosign library in Kyverno v1.11.5 cannot read.
- Inline runtime agent gateway: the `internal/gateway` package holds the admission decision the Phase 4 agent layer turns on (`Decide(registry, request) → Decision`) — a request is allowed only when the agent is registered and the prompt and every tool it uses are ones the agent declares — and a `Server` HTTP handler that serves that decision at request time (200 admit / 403 block with a reason) and appends every handled interaction to a JSON-lines log. `fabric gateway <registry-dir> [--addr <addr>] [--log <path>]` runs it; the network `ListenAndServe` shell is the only part outside the test-first core. This is the inline counterpart to the after-the-fact `fabric trace`: both now share one definition of "qualified" through `gateway.Decide`, so a request the gateway blocks inline is exactly a trace that rolls up as not-satisfied.
- `evidence.FromAgentTraces` now also accepts the gateway's JSON-lines interaction log (one object per line) in addition to the `{"traces":[...]}` envelope, so the gateway's own record of what it enforced is consumable as control evidence with no reshaping step.
- Gateway content guardrail: `gateway.GuardrailPolicy` is a set of named regexp content rules (in Git, reviewed like any other policy), `CompileGuardrail` compiles them up front so a bad pattern is caught before the gateway serves, and `Guardrail.Screen` blocks a request whose input matches a rule, naming the rule that fired. The `Server` now composes two checks — the registry decision (may the agent act at all) then the content guardrail (may this input pass), first denial wins — and `fabric gateway --guardrail <policy-file>` loads and compiles the policy. The interaction log records the verdict but never the raw input, since that input may be the sensitive data a guardrail caught. This advances the gateway from registration-only enforcement toward the input/output content policy the agent-governance layer describes.
- Gateway model allow-list: `gateway.Decide` now also screens the model a request declares (`Request.Model`) against the agent's qualified `registry.Agent.Model`, blocking a request that asks for an off-list model ("agent X is not qualified for model Y"). The check is non-strict by design — it fires only when the request declares a model and the agent pins one, so a request that declares no model is not model-screened (the gateway screens what the caller asserts) and the post-hoc trace-evidence path, which re-derives the same decision without a model, is unaffected. The interaction log now records the model and an input/output `phase` per entry.
- Gateway output screening: the `Server` now screens generated output, not just input. A `POST /output` with an `OutputRequest` (`{id, agent, prompt, output}`) runs the output through the same compiled guardrail and replies 200 when it may pass or 403 when a rule catches it, logging the verdict — never the raw output, which may itself be the sensitive data the guardrail caught — as a `phase:"output"` interaction the evidence path can attribute. Output screening is content-only (the agent already passed input admission), so the registry check is not repeated. This delivers the "policy on inputs **and** outputs" the agent-governance layer describes.
- CI-only keyless admit-path e2e (`test/e2e/keyless-ci.sh`) and a `keyless-e2e` CI job with `id-token: write`: it signs a test image with the GitHub Actions OIDC identity (no key material), applies the production `verify-image-signatures.yaml` policy verbatim on a kind cluster, and asserts the unsigned image is denied and the keyless-signed image is admitted. This exercises the one Phase 2 strand that cannot run locally (keyless signing needs an OIDC provider); the job is skipped on forks, which cannot mint the repository's OIDC identity. Both kind-based e2e jobs (Phase 1 admission and Phase 2 keyless) now pass in CI — the first time the cluster-based proofs run green there rather than only locally.
- End-to-end proof of the inline agent gateway (`test/e2e/gateway.sh`), wired into CI as the `gateway-e2e` job: it runs the real `fabric gateway` HTTP server against the starter registry and a content guardrail, then asserts over live requests that a qualified interaction is admitted (200), an unregistered agent is blocked (403), and a registered agent whose input carries a sensitive-data pattern is blocked (403) without the raw input ever reaching the log; it then feeds the gateway's own log through `fabric trace` and asserts the admitted interaction is satisfied while both blocked interactions are not-satisfied, and the ledger chain verifies. This exercises the `ListenAndServe` network shell that the unit tests cannot, closing the gap between the test-covered decision and the running server.
- End-to-end proof of SBOM-content evidence from a real syft scan (`test/e2e/sbom.sh`), wired into CI as the `sbom-e2e` job: it runs syft over a container image to produce a genuine CycloneDX SBOM, then asserts `fabric sbom` blocks a banned component that is actually present (not-satisfied, non-zero exit) and admits a policy that bans only absent components (satisfied, ledger chain verifies, posture clean). This closes the gap between "parses a hand-written fixture" and "parses what syft emits".
- Producer registry (`internal/collect`): the seven evidence producers are now registered behind a uniform `Producer func([]byte, Params) ([]Record, error)` signature in a `Producers` map keyed by source type, dispatched through `collect.Run`. One definition of each producer is shared by the CLI subcommands and the continuous collector, so adding a source type wires both at once and the two can never drift apart.
- Live posture dashboard (`internal/dashboard`) and `fabric serve <ledger-path> [--addr <addr>]`: a read-only HTTP surface over the control-posture rollup that re-reads the ledger on every request, so the page reflects what the continuous collector is appending in real time. The root path renders an HTML table — one row per control with its current status, observation count, lapses, and last-observed time, gaps highlighted and a satisfied/gaps summary line — and `/posture.json` serves the same rollup machine-readably with a `{total, satisfied, gaps}` summary a monitor can gate on. It is the live counterpart to the one-shot `fabric ledger posture` table. The rendering and routing (HTML/JSON, 404/405, live re-read) are TDD-covered against an in-memory source; the ledger read is validated up front so a bad path fails before the listener binds, leaving `ListenAndServe` as the only untested edge.
- Optional `artifact-ref` on evidence records (`evidence.Record.ArtifactRef`): `fabric provenance` records each attested artifact's content digest (`sha256:<hex>`) and `fabric sbom` records the scanned image's digest, so a content or provenance record links back to the exact artifact — and thus to its transparency-log entry, since a transparency log is indexed by that same digest. The field is omitted when no digest is present, so records that do not concern an artifact are unchanged.
- Coverage-over-time trend (`posture.TrendOf`): it replays the append-only ledger in chronological order into a satisfied/total-per-moment series (latest-result-wins per control, same-instant observations collapsed), a faithful history rather than a sampled approximation because the ledger is an event log of state changes. The dashboard now renders it as an inline-SVG sparkline ("Coverage trend") alongside the current rollup, and `fabric serve` exposes it machine-readably at `/trend.json` (`{"points":[{at, total, satisfied}]}`) a monitor can chart. This is the trend half of the `docs/07` reporting surface (live coverage, current gaps, **and trend**).
- Release evidence gate (`internal/release`) and `fabric release-gate <manifest-file> [--ledger <path>]`: a declarative release manifest (`release/manifest.json`) names each generated supply-chain artifact (the SBOM, the SLSA provenance attestation) and the producer that judges it; the gate runs every producer once over those files, appends the resulting records to a fresh per-release ledger, verifies the chain, and clears the release (exit 0) only when every control is satisfied — so a banned component, an artifact built outside the trusted pipeline, or a failed evaluation gate blocks the ship (exit 1). It reuses the shared `internal/collect` producer registry, so a release-time judgment and an after-the-fact one are identical; `LoadManifest` validates the manifest up front (at least one source, every source a known producer with a non-empty artifact file) and the gate decision (`Blocking`) is unit-covered, leaving only file and ledger I/O in the CLI shell. This binds the generation harness into the release pipeline rather than leaving it as an e2e proof.
- Release pipeline (`.github/workflows/release.yml`): on a tagged release it builds `fabric`, generates a real CycloneDX SBOM of the released tree with syft, runs `fabric release-gate` over `release/manifest.json` (banned-components policy in `release/sbom-policy.json`), verifies the resulting ledger, and uploads the verified ledger and the SBOM as release evidence artifacts. The trusted-builder identity in the supply-chain evidence (`.github/workflows/release.yml@refs/heads/main`) now refers to this real workflow.
- End-to-end proof of the release gate (`test/e2e/release.sh`), wired into CI as the `release-e2e` job: it generates a genuine syft SBOM, pairs it with a SLSA provenance attestation in one release manifest, and asserts the gate clears a clean release (the verified ledger is the evidence artifact) and blocks both a banned component that is actually present and provenance from an untrusted builder. This proves the release gate over the real generation harness rather than fixtures alone.
- Cross-sector crosswalk (`internal/crosswalk`) and `fabric crosswalk <crosswalk-file> <source-ledger> [--ledger <path>]`: the start of Phase 5. A crosswalk maps a target-sector citation onto the controls the Fabric already enforces and evidences, and `crosswalk.Apply` rolls a source ledger's existing evidence up under those citations — one derived record per mapping. A target citation is satisfied only when **every** anchor control it maps to is currently satisfied (a missing or not-satisfied anchor makes it not-satisfied), where "currently satisfied" is posture's latest-observation rule, reused so a crosswalk conclusion can never disagree with the posture view it is built from. The derived record carries no new raw evidence; its source names the anchor controls behind it, so a second-framework citation traces straight back to the single enforced control that answers it. With `--ledger` the derived records append to a ledger that verifies, so the cross-sector rollup becomes durable evidence like any other; the exit code is non-zero when any target citation has a gap. This is the "one control, many regulations" claim made concrete: the same enforced GxP control answers a finance/critical-infrastructure citation with no new enforcement code.
- A DORA catalog (`controls/catalogs/dora.json`, Regulation (EU) 2022/2554) and a worked DORA crosswalk (`controls/crosswalks/dora.json`) that answers four DORA citations — access management, logging/traceability, ICT risk-management/change-control, and ICT supply-chain — from the existing Part 11, Annex 11, and supply-chain controls, demonstrating the crosswalk end to end on real project controls.
- A NIS2 catalog (`controls/catalogs/nis2.json`, Directive (EU) 2022/2555) and a worked NIS2 crosswalk (`controls/crosswalks/nis2.json`) answering four Article 21(2) measures — supply-chain security (d), secure development/maintenance (e), effectiveness assessment (f), and access control (i) — from the same Part 11, Annex 11, and supply-chain anchor controls. A CLI test exercises the shipped artifact directly, proving the committed crosswalk is valid and wired to anchors that exist. This is the second sector on the same engine: the crosswalk generalizes beyond a one-off.
- Crosswalks are now first-class control-tree artifacts: `loader.Load` reads `<root>/crosswalks/*.json` into the bundle, and `fabric validate` checks each crosswalk's referential integrity against the catalogs — every anchor a citation is `satisfied-by` resolves to a real control (`crosswalk-unresolved-anchor`), the target citation is a real control (`crosswalk-unresolved-target`), no citation is mapped twice (`crosswalk-duplicate-target`), and no citation is answered by nothing (`crosswalk-empty-mapping`). A typo'd anchor id — which would otherwise silently make a citation un-satisfiable at runtime — is now caught at validate time, the same rigor profiles and component definitions already get.
- Continuous collector (`internal/collect`) and `fabric collect <config-file> --ledger <path> [--once]`: it polls a declarative set of sources on an interval — each source naming a producer type, the fetch command that obtains its input (for example `kubectl get applications -o json`), and the aux references that resolve into the producer's parameters — and appends **only the state changes** to the ledger. `collect.LoadConfig` validates and resolves the whole config up front (interval parses, every source names a known producer and a non-empty command, every referenced aux file loads), so the collector never starts on a config that would fail mid-run. `Dedup` gives the ledger event-log semantics: a record is appended only when the `(control, subject)` result transitions, so a stable control does not write a "still satisfied" row every tick, yet posture's latest-wins rollup still reports it correctly. A source that fails to fetch or produce degrades that source rather than aborting the tick. `--once` runs a single tick (testable and CI-driveable); without it the collector loops on the configured interval. The fetch (process execution) and the ticker loop are the only parts outside the test-first core.

### Changed

- The `fabric` producer subcommands (`policy-report`, `drift`, `eval-gate`, `provenance`, `sbom`, `trace`) now dispatch through the shared `collect.Run` registry instead of calling each `evidence.FromX` function directly, so the CLI and the continuous collector run identical producer code. File and aux-reference parsing stays at the CLI edge; the producer logic is the registered one.
- `evidence.FromAgentTraces` (and so `fabric trace`) now also accepts the OpenTelemetry OTLP/JSON trace export (`{"resourceSpans":[…]}`) alongside the `{"traces":[...]}` envelope and the gateway's JSON-lines log. Each span is flattened into one interaction: its attributes (`id`, `agent`, `prompt`, `tools`, and the gateway's recorded `allowed` verdict) mirror the JSON-lines field names, the span id is the interaction id when no `id` attribute is set, and the span's `startTimeUnixNano` is the observed time. This realises the docs/05 claim that agent actions are traced with OpenTelemetry — a standard OTel trace pipeline can feed the evidence ledger with no reshaping step.
- `evidence.FromAgentTraces` now honors the gateway's recorded verdict: a JSON-lines interaction logged as `allowed:false` rolls up as not-satisfied even when the agent, prompt, and tools are all registered — so a request the gateway blocked on **content** (a guardrail match), not just on registration, is faithful in the evidence rather than silently re-derived as satisfied from the registry surface alone. A trace with no recorded `allowed` field (the `{"traces":[...]}` envelope an OTel pipeline produces) is still judged against the registry by `gateway.Decide`, so both shapes remain correct.

- `fabric policy-report` now accepts the List shape `kubectl get policyreport -o json` returns when a namespace holds more than one report (Kyverno writes one report per resource), and derives the evidence subject from a report's item-level `scope` when results carry no per-result `resources` — so live background reports yield subject-bearing evidence, not just the single-report fixture shape.
- The kind-based CI jobs install `kind`/`kubectl` by downloading to the workspace and `sudo mv`-ing them into place (a direct write to `/usr/local/bin` is denied on GitHub-hosted runners), and the e2e harnesses wait for all Kyverno deployments to be `Available` and retry the first policy apply (Kyverno's policy webhook starts serving a moment after the deployment reports Ready, so the first apply otherwise races it with "connection refused").
- Renamed the project from "GxP Compliance Fabric" to "Compliance Fabric" across documentation and metadata.
